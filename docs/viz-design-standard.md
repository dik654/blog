# Blog Viz design standard

이 문서는 새 Viz와 레거시 Viz 재작성에 공통으로 적용하는 기준이다. 참고 자료는
`concept-reels-creator`와 `무지성PPT생성기`이지만, 두 자료의 장식을 그대로 복제하지
않고 개념 전달 방식과 검수 절차만 가져온다.

## 1. 먼저 개념을 설계한다

- 한 Viz에는 한 가지 메커니즘만 담는다.
- 제목과 나열만 있는 카드 모음 대신 `원인 → 계산/상태 변화 → 결과`를 그린다.
- 비교라면 같은 축과 같은 예산을 사용한다. 계보가 아닌 것을 시간순 진화로 포장하지 않는다.
- Primitive 교체와 execution/proof-layer 최적화처럼 설계 방향이 반대인 비교는 가운데에 고정 workload를 두고 양쪽이 무엇을 바꾸는지 화살표로 보여 준다. 제품·논문 이름을 카드로 나열하는 것만으로 방향 전환을 표현하지 않는다.
- Roadmap Viz는 시간축만 그리지 않는다. 각 node에 `배포 / 검토 / 연구 / 실험` 상태를 모양과 짧은 label로 함께 표시해 연구 후보가 확정 일정처럼 보이지 않게 한다.
- 초심자는 그림만 보고 흐름을 말할 수 있어야 하고, 전문가는 변수·전제·병목을 확인할 수 있어야 한다.
- 블록 안에는 짧은 명사구와 핵심 숫자만 둔다. 두 문장을 넘는 설명은 Viz 바깥으로 옮긴다.
- 약어와 전문용어만으로 만든 계보·분류표를 글의 첫 Viz로 쓰지 않는다. 먼저 독자가 붙잡을 핵심 아이디어와 입력→변환→출력 관계를 보여 준다.

## 2. 시각 규칙

- gradient, glow, blur 장식, dot-grid 배경을 사용하지 않는다.
- 외곽선과 connector는 기본 `1px`, 강조도 `1.25px`를 넘기지 않는다. 아이콘은 `1.5–1.75px`를 쓴다.
- 색은 의미를 구분하는 한 가지 accent와 상태색만 쓴다. 색만으로 상태를 구분하지 않는다.
- 중첩된 카드 프레임과 큰 radius를 반복하지 않는다. radius는 기본 8–12px이며 shadow는 사용하지 않는다.
- canvas 안쪽 안전 여백은 폭의 약 4% 이상, 주요 컴포넌트 사이 간격은 모바일 16px, 데스크톱 24px 이상이다.
- SVG `<text>`에 긴 문장을 넣지 않는다. HTML 레이아웃이나 `foreignObject`를 쓰되 높이를 고정한 채 내용을 숨기지 않는다.
- 좁아지면 억지로 축소하지 말고 세로 배치 또는 가로 스크롤로 전환한다.
- 서로 다른 연구 축이 한 구조에서 합쳐질 때는 한 축이 다른 축으로 진화하는 timeline으로 그리지 않고, 각 병목과 mechanism이 결합 지점으로 수렴하는 branch diagram을 사용한다.
- 여러 컷을 넘기는 Viz는 pointer 버튼만 두지 않는다. Viz 자체를 keyboard focusable하게 만들고 `←`·`→`로 이전·다음 컷, `Space`로 재생·일시정지를 제공하며 화면에 단축키를 표시한다. 입력 필드와 contenteditable의 키는 가로채지 않는다.
- 개념마다 여러 컷을 갖는 Viz에서 `다음`으로 개념 경계를 넘으면 새 개념의 첫 컷으로 이동한다. 반대로 첫 컷에서 `이전`으로 돌아가면 이전 개념의 마지막 컷을 보여 전체 탐색 순서가 단조 증가·감소하게 유지돼야 한다.
- 장면을 바꿀 때 Viz 외곽 frame과 이전·재생·다음 control row의 위치가 움직이지 않아야 한다. 모든 장면의 필요한 크기를 기준으로 stage의 안정된 높이를 확보하고, control은 그 stage 아래의 고정된 row에 둔다. 현재 장면 내용 높이에 맞춰 wrapper 자체를 매번 줄였다 늘리지 않는다.
- 안정된 stage는 데스크톱에서도 viewport를 넘어 버튼이 화면 밖으로 밀리지 않게 `100dvh`에서 page header·caption·control 여백을 뺀 상한을 둔다. 큰 장면은 frame을 키우는 대신 stage 내부의 responsive 재배치, 축척 또는 명시적 scroll 영역으로 처리한다.
- 모바일은 장면별 긴 설명을 stage 안에 모두 쌓아 최소 높이를 무한히 늘리지 않는다. diagram과 현재 핵심 설명을 안정 영역에 두고, 상세 설명이 상한을 넘으면 stage 내부에서만 스크롤하되 control row는 바깥에 남긴다.
- 같은 Viz의 모든 장면에서 control button의 bounding box 변화는 2px 이내, frame top/left/width 변화는 2px 이내를 목표로 한다. Reduced motion 여부와 관계없이 layout shift 자체는 없어야 한다.

## 3. 수식 규칙

모든 주요 KaTeX 식은 다음 순서를 따른다.

1. 이 식이 답하는 질문
2. 식을 그렇게 만든 설계 아이디어
3. KaTeX 식
4. 기호의 역할, 성립 전제, 식에서 읽어야 할 결과

새 글은 `ExplainedFormula`를 사용한다. 식을 먼저 보여 주고 아래에서 뒤늦게 뜻을 설명하지 않는다.

## 4. 검수 게이트

- 코드 검사: gradient, 굵은 stroke, 과도한 radius/shadow, SVG 긴 텍스트를 찾는다.
- 브라우저 검사: 데스크톱과 모바일에서 text overflow, label-box, label-line, canvas overflow를 확인한다.
- 장면 전환 검사: 첫 장면·가장 큰 장면·마지막 장면에서 frame과 control button bounding box를 기록해 위치·크기가 2px 넘게 변하지 않는지 확인한다. 또한 frame bottom과 control row가 viewport 안에 동시에 들어오는지 검사한다.
- 스크린샷 검사: 좌표 검사를 통과해도 실제 폰트가 벗어날 수 있으므로 렌더 결과를 직접 본다.
- 한 화면이 빽빽하면 글자를 줄이지 않고 Viz를 둘로 나눈다.

`npm run audit:viz -- <바꾼 파일 또는 디렉터리>`로 정적 검사를 실행한다. 레거시 전체
경고는 이관 목록으로 관리하고, 새로 작성하거나 손댄 Viz에는 예외를 추가하지 않는다.
