# AI 서빙 묶음 02 · 요청에서 실행 선택까지

작성일: 2026-10-24
범위: `ai/vllm-serving`, `ai/serving-latency-metrics-and-slo`, `ai/vllm-scheduler`

## 묶음의 직속 부모

Transformer가 요청별 KV 상태를 만든다는 사실에서 출발합니다. 추론 엔진은 그 상태를 이용해 한 요청을 다음 여덟 결정으로 처리합니다.

1. 요청: 입력을 실행 상태로 바꾸고 출력을 돌려줍니다.
2. 측정: 첫 출력과 이후 간격을 따로 기록합니다.
3. 선택: 이번 실행에 넣을 요청과 token 수를 정합니다.
4. 묶음: 실행 경계마다 진행·완료·신규 요청을 다시 구성합니다.
5. 단계: prefill과 decode의 서로 다른 계산 모양을 함께 다룹니다.
6. 기록: KV 상태를 block 단위 물리 공간에 배정합니다.
7. 수용: 메모리가 부족할 때 대기·선점·재계산을 결정합니다.
8. 재사용: 조건이 같은 앞부분의 KV block을 공유합니다.

이번 배치는 1~3을 연결합니다. 4~8은 다음 글들의 직속 부모 지도에 이미 표시하고 차례대로 보강합니다.

## 글 분류

| 글 | 트랙 | 이 글이 답할 질문 |
|---|---|---|
| vLLM 입문 | concept | 요청의 진행 상태와 token·요청·KV 예산은 매 실행에서 어떻게 연결되는가? |
| 지연 지표와 SLO | concept | 사용자가 겪은 첫 기다림과 출력 중 멈춤을 어떻게 서로 다른 값으로 보존하는가? |
| vLLM Scheduler | concept | 남은 계산량과 예산·공간에서 이번 실행의 배정량을 어떻게 확정하는가? |

세 글에서 vLLM은 제품 선택안이 아니라 메커니즘을 확인하는 고정 원문 구현입니다. 배포 버전 선택, 운영 SLO 수치, 용량 정책은 별도의 실무 글에서 결정합니다.

## 보존한 근거

- vLLM 입문의 A·B·C 요청 trace, token·sequence·KV feasibility, frontend→engine core→executor 경계와 고정 원문을 유지했습니다.
- 지연 글의 다섯 token 도착 시각, TTFT·ITL·TPOT·E2E 계산, percentile 정의, 누락 구간을 포함한 SLO 판정과 실제 benchmark 코드를 유지했습니다.
- Scheduler 글의 예산 5에서 R1·R2·P를 배정하는 사례, chunked prefill, policy, preemption, VTC 경계와 고정 원문을 유지했습니다.
- 측정하지 않은 처리량·지연 개선을 결과처럼 쓰지 않았습니다.

## 이번 변경

- 세 글이 같은 `ServingEngineSeriesLocator`를 사용해 요청 하나가 거치는 여덟 결정을 본문보다 먼저 보여줍니다.
- 각 글의 현재 결정과 확인할 결론을 지도 안에서 표시합니다.
- 글 끝에서 확인한 사실을 같은 지도에 되돌리고 다음 결정으로 연결합니다.
- 모바일에서는 여덟 단계를 2열로 배치해 첫 지도와 현재 결론을 짧은 이동 안에서 볼 수 있게 했습니다.
- 세 경로를 JavaScript 비활성 정적 본문 생성 목록에 등록했습니다.
