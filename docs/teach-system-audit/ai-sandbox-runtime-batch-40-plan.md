# AI 샌드박스 런타임 경로 · Batch 40

## 범위

이 글은 앞 글에서 허용된 보고서 요약 코드가 실제 샌드박스 안에서 실행되는 지점부터 시작합니다.

1. 생성 코드는 `openat(AT_FDCWD, "/workspace/report-91.md", O_RDONLY)`를 호출합니다.
2. Seccomp는 호출을 허용하거나 거부하지만, 허용된 호출은 공유 호스트 커널이 처리합니다.
3. gVisor에서는 Sentry가 애플리케이션의 Linux 시스템 API를 구현합니다.
4. Kata에서는 VM 안의 게스트 커널이 호출을 처리하고 VMM이 호스트 상호작용을 중재합니다.
5. 세 경로 모두 파일·통신·자격증명·자원 정책을 별도로 구성해야 합니다.

## 학습 지도

직속 부모 지도는 샌드박스 경계를 네 단계로 나눕니다.

`프로세스 → 시스템 호출 → GPU 장치 → 배포 통제`

이 글은 `시스템 호출`을 맡습니다. Seccomp·gVisor·Kata를 한 줄의 보안 등급으로 세우지 않고, 같은 호출을 누가 처리하는지와 어떤 경계가 남는지를 부모 지도에 반환합니다.

## 공식 근거

- Linux kernel Seccomp BPF 문서에서 호출 번호·인자와 ALLOW·ERRNO·TRAP·KILL 반환 경계를 확인했습니다.
- Kubernetes Seccomp 문서에서 `RuntimeDefault`와 컨테이너 런타임별 기본 프로필 차이를 확인했습니다.
- gVisor `release-20261019.0`의 Security Model에서 Sentry의 시스템 API 구현과 제한된 호스트 인터페이스를 확인했습니다.
- Kata Containers `4.3.1`의 virtualization 문서에서 게스트 커널·VMM·가상 장치 경로를 확인했습니다.

## 작성 원칙

- 첫 설명보다 먼저 같은 `openat()` 호출의 세 경로를 시각화합니다.
- Seccomp의 호출 필터와 파일 경로 권한을 같은 기능으로 설명하지 않습니다.
- Sentry와 게스트 커널을 모두 단순한 “더 강한 컨테이너”로 뭉개지 않습니다.
- 장면은 명시적인 재생과 이동에만 반응합니다.
- JavaScript가 꺼져도 다섯 장면과 결론을 같은 순서로 읽을 수 있게 정적 본문을 생성합니다.
