# Scene Spec 작성 가이드 — Primitives-first Pedagogy

Scene 엔진의 `description`, `why`, `notes` 필드를 쓸 때 따르는 글쓰기 원칙.
**핵심: 결론 / 전문용어로 시작하지 말고, 단순 케이스의 한계 → 새 조각의 구체적 기여 → 일반화 관계 순으로 쌓아 올린다.**

## 왜 이 패턴인가

블로그 독자가 "왜?" 라고 물었을 때, 답이 또 다른 전문용어로 채워지면 그 용어가 새 질문이 됨.
"왜 비선형이 필요해?" → "표현력을 위해" → "표현력이 뭔데?" → "임의 함수 학습 가능…" → 끝없음.

대신 단순 케이스 ($s \cdot h_i$) 의 구체적 한계 → 새 조각이 그 한계를 어떻게 푸는지 → 새 식이 단순 케이스를 특수 경우로 포함한다는 관계로 정리하면, 추가 질문이 자연스럽게 사라짐.

## 4 단계 패턴

### 1. 단순 케이스 / 출발점부터 시작
- "가장 단순한 X 는 …" 으로 출발
- 그 단순 케이스가 어떤 모양의 함수만 표현 가능한지 **구체적으로** 짚음
- 결론 (universal approximation, 표현력, bilinear 등) 던지지 않음

```
✗ 비선형 활성화가 표현력을 늘려준다 (universal approximation)
✓ 가장 단순한 유사도는 $s \cdot h_i$ — 두 벡터의 같은 위치끼리 곱하고 합한 값.
  그 한 가지 모양만으론 모든 종류의 유사도 패턴을 표현 못 함
```

### 2. 새 조각의 구체적 기여
- 새 조각 (tanh, W, $v^T$ 등) 이 무엇을 더하는지 **결과로** 설명
- "비선형이 들어가서 표현력 늘어남" 이 아니라 "휘지 않으면 매트릭스 두 층이 한 매트릭스와 같아짐 → 두 층 쌓은 의미가 사라짐. tanh 가 한 번 들어가야 두 층의 효과가 살아남"

```
✗ tanh 는 비선형 활성화 함수
✓ S 자 모양으로 휘는 함수.
  휘지 않으면 (선형) 매트릭스 두 층은 결국 한 매트릭스와 같아짐 — 두 층 쌓은 의미가 사라짐.
  tanh 가 한 번 들어가야 두 층의 효과가 살아남
```

### 3. 학습 가능 가중치가 뭘 학습하는지 구체적으로
- "어떤 가중치 학습" → "**어느 차원의 패턴이 점수에 중요한지** 학습"
- "어떤 변환 학습" → "**입력의 어느 부분을** 추출할지 학습"

```
✗ $W_Q$ 는 학습되는 선형 변환
✓ $x$ 의 각 차원에 어떤 가중치 줘서 합산할지 결정.
  결과 $Q$ 의 각 차원이 "찾고 싶은 정보" 의 한 측면을 담음
```

### 4. 일반화 관계 — 단순 케이스가 특수 경우
- 새 식이 단순 케이스를 어떤 파라미터 설정으로 환원하는지 명시
- 이렇게 하면 일반성이 어디서 오는지가 자연스레 보임. 별도의 "표현력" 단어 불필요

```
✗ MLP 는 더 표현력이 좋다
✓ vs $s \cdot h_i$: dot product 는 위 식에서 $W = U = I$, tanh 빼고, $v$ 가 전부 1 인 특수 케이스.
  이 식이 그보다 일반적이라 dot product 가 못 잡는 유사도도 학습 가능
```

## 고급 이름은 마지막에

- "이게 universal approximation 이라고 부르는 정리의 결론" 식으로 **이름을 결론에 붙임**
- 이름이 본문 한가운데서 갑자기 튀어나오지 않게

## 캡션 ↔ inputs 일관성 규칙 (필수)

`transition.caption` 의 수식에 등장하는 **모든 객체 심볼** 은 `transition.inputs` 에 들어가야 한다.
그래야 시각적으로 그 객체에서 produces 로 화살표가 그려지고, 독자가 "이 항은 어디서 왔지?" 라는 질문을 하지 않게 된다.

### 검사 방법

캡션의 수식을 풀어 적은 뒤, 각 항이 어떤 객체에서 오는지 매핑.
- 매핑되는 객체가 `inputs` 에 없으면 → 추가.
- 매핑되는 객체가 없으면 → 중간 객체를 만들어 이전 transition 의 produces 로 두든지, 캡션을 바꿔서 그 항을 제거.

### 좋은 예 — Bahdanau t=1

캡션: `$e_j = v^T \tanh(W s + U h_j)$`
등장 객체: $v$, $W$, $s$, $h_j$ (= group $H$ 의 원소), 그리고 합성 항 $W s$.
이미 t=0 에서 $W \cdot s$ 가 `Ws` 객체로 만들어졌으므로:

```ts
{ t: 1, op: 'project', inputs: ['Ws', 'H', 'U', 'v'], produces: 'e', ... }
```

→ `Ws → e`, `H → e`, `U → e`, `v → e` 4 개 화살표가 그려져 캡션의 모든 항이 시각적으로 e 로 모임.

### 나쁜 예

```ts
{ t: 1, op: 'project', inputs: ['H', 'U'], produces: 'e',
  caption: '$e_j = v^T \tanh(W s + U h_j)$' }
```

→ 화살표는 H→e, U→e 만 있어서 캡션의 $W s$, $v$ 가 "어디서?" 가 됨.

### 한계 케이스

- 합성 항을 별도 객체로 만들 가치가 있으면 만들어라 (예: $Uh_j$ 가 의미적으로 중요하면 `Uh` 객체 만든 뒤 별도 transition).
- 만들 가치가 없을 만큼 자명하면 (예: $v$ 같은 학습 파라미터) 그냥 inputs 에 넣어 직접 연결.
- 캡션이 너무 복잡하면 transition 을 둘로 쪼개기.

## Caption / Why / Notes 분담

| 필드 | 역할 | 예시 |
|---|---|---|
| `caption` | 한 줄 수식 또는 핵심 명칭 | `$e_i = v^T \tanh(W s + U h_i)$` |
| `why` | 이 연산을 왜 하는지 (3-4 문장) | 단순 케이스 한계 → 어떻게 푸는지 |
| `notes` | 수식 요소별 풀이 (각 1-3 문장) | `$\tanh(\cdot)$`: S 자 모양으로 휘는… |

`notes` 의 `tex` 필드는 **수식의 한 조각**, `note` 는 그 조각의 **무엇 + 왜**.

## Description / Why (Object)

| 필드 | 역할 |
|---|---|
| `description` | 한 줄 — 이 객체가 **무엇** 인지 (역할만) |
| `why` | 이 객체가 **왜** 이런 형태인지 (별도 매트릭스인 이유, 차원 결정 이유 등) |
| `notes` | shape 의 각 차원 의미 등 |

## 문장 끝 줄바꿈

`.`, `?`, `!` 뒤 공백은 자동으로 줄바꿈됨 (TeX 컴포넌트 처리).
따라서 한 `why` 안에 여러 문장 자유롭게 — 각 문장이 자기 줄에 놓임.

## 좋은 예 — Bahdanau MLP (참조 모델)

`src/components/scene/types.ts` 의 `EXAMPLE_ADDITIVE_ATTN` t=1 transition 이 이 패턴의 표준 예시.
이 글을 새 spec 작성 시 모범으로 사용.

## 안 좋은 예 — 피해야 할 패턴

- "표현력이 늘어난다" / "유연하다" / "강력하다" — 추상 형용사
- "universal approximation", "bilinear", "hidden layer" — 풀어쓰지 않은 전문용어
- "왜?" 질문에 또 다른 결론으로 답하는 순환

## 적용 시점

- 새 spec 작성 시 처음부터 이 패턴
- 기존 spec 도 마이그레이션 (attention-theory 실 글 등) 진행 시 함께 정리
- pilot 의 미정리 spec 부분은 마이그레이션 때 한꺼번에 적용
